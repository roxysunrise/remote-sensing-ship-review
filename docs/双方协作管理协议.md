# 双方协作管理协议

日期：2026-10-27（Asia/Shanghai）

版本：v0.2（职责调整提案），经双方确认并合入 main 后生效；B 方尚未确认。
适用项目：遥感船舶检测与人机协同复核系统。

## 1. 角色与责任

| 角色 | 主责 | 交付 |
|---|---|---|
| A 方 | 船舶检测模型、训练与评估、大图切片及推理、旋转框几何与编辑核心、AI 辅助标注计算、疑难复核策略、计算任务 Worker 与运行环境；图像验证、预览处理、存储及可恢复上传基础封装、计算端权限边界评审 | 可调用的算法与计算服务、可嵌入核心组件、接口与样例、实验记录、启动及验证说明 |
| B 方 | 前端页面及交互集成、常规业务后端与数据库、账号项目及成员业务、影像资产与检测任务记录、人工修订及版本管理、区域统计与报告导出、AI 候选确认流程、业务测试 | 可运行的前后端应用、业务 API、数据保存与查询、工作台和业务流程、使用说明及可复现验收记录 |
| 双方 | 公共接口与数据语义、鉴权及文件权限边界、存储和上传衔接、系统联调、异常恢复、业务验收与演示 | 真实端到端流程、接口约定及共同验收证据 |

模块主责以交付结果划定：A 负责复杂算法、几何与计算基础，不代替 B 完成常规业务后端和页面；B 负责业务接口、数据存取与应用体验，不重复开发模型训练、检测推理或旋转框几何内核。双方协作不意味着同一模块由两人重复实现。

跨界接口和数据契约通过 `contracts/` 与关联 PR 确认，尤其明确坐标格式、状态唯一来源、数据归属、取消重试、修订版本和权限规则。未确认的草案可用于并行开发，但不能单方面成为最终约定。

具体数据写入责任、任务可靠性、上传和权限、组件交付、版本统计与联合验收，见[模块边界与验收细则](模块边界与验收细则.md)。该细则属于本职责调整提案，不代表功能已实现；双方确认后与本协议同时生效。

## 2. 并行开发与接口规则

1. 双方可自行选择模块直接开发，不安排必须等另一方先完成 API 的串行流程。
2. 开工前快速查看 main、相关 Issue、未合入 PR 和 contracts，避免重复实现。
3. 已有共同接口或组件约定时遵守它；确需调整时提交变更说明。
4. 缺少接口时，当前开发者可自行提出路径、请求响应、错误、数据类型和样例，并继续实现。双方可使用明确标识的模拟数据推进各自模块；对应服务由该模块的主责方实现。
5. 新约定尽早放入草稿 PR，并关联 Issue，让对方看到。提出者无须等待审阅才编码，但未合入草案不自动约束对方。
6. 跨双方的接口由另一方确认；合入 main 后成为共同标准。不能以“先写完代码”为理由单方面确定公共约定。
7. 同时产生不同草案时，在关联 Issue/PR 中按业务需求、已有调用和改动成本选定一套，同时更新实现、文档、样例及调用方。
8. 接口描述、实现和样例随同一 PR 更新，或用明确关联的配套 PR 更新；需要配套才能运行的变更不得单边合入破坏 main。

## 3. 公共约定的唯一来源

- HTTP API：contracts 下的一份 OpenAPI 描述及其引用文件；技术栈确定后建立，当前不虚构完整 API。
- 编辑组件：组件导出的属性、事件、数据类型及使用示例。
- 业务语义：坐标与角度、任务状态、结果版本、区域计数、AI候选确认、错误与权限规则在 contracts 中明确记录。
- 模拟数据遵守相同约定并标识用途；不能用模拟数据通过真实能力验收。
- 模块内部实现由负责人决定；删除字段、改类型、增加必填项或改变状态/计数含义，必须通知调用方并提供迁移安排。
- 生成的文档、类型或客户端不手工维护第二套；生成方式确定后记录命令。

## 4. GitHub 工作流

- 一个仓库，main 为共同集成基线，保持在当前实现范围内可运行；当前初始化阶段仅有文档。
- 每个可验收功能使用短期分支，如 codex/upload-resume、codex/review-page；不使用长期 A/B 分支。
- Issue 写明目标、范围、负责人和验收方法；相关分支与 PR 引用同一 Issue。
- 通过 PR 合入，禁止日常直接推送 main、强推 main 或重写共同历史。首次初始化提交例外。
- PR 写明功能、接口影响、启动方式、验证证据、已知限制与对方接入步骤。
- 公共接口和核心业务语义变更由另一方审阅；纯内部文档或局部实现可在检查通过并通知对方后自行合入。
- main 有回归时先修复或用新提交回退问题变更，不用强推抹除历史。
- 在账号计划允许时用分支规则强制 PR 与适当检查；尚未启用或不可用时以上规则由双方人工执行，不能称为已强制保护。

## 5. 状态与交付标准

使用 Issue 标签记录：开发中、可接入、已接入、已验收；未创建的标签不代表已配置看板。

“可接入”要求：真实功能或明确标识的前端模拟实现、接口/组件约定、正常与错误样例、依赖与启动方法、验证结果和已知限制齐全。

“已接入”要求：双方代码已打通。使用模拟数据不能计为真实计算能力已接入。

“已验收”要求：指定版本在真实环境完成相应用户流程，保留环境、提交号、样例和结果。模块可运行不等于全系统完成；模型精度、坐标正确性和业务一致性分别验证。

## 6. 检查与发布

技术栈确定后逐步接入接口合法性与兼容性、前端类型和构建、后端关键行为以及核心流程检查。每个 PR 运行与改动相关的必要检查；未运行和无法验证的内容必须注明。当前尚无代码 CI，不宣称检查已自动执行。

联调环境显示提交版本、模型版本和示例/真实任务标识。阶段验收通过后使用版本标签记录共同基线。部署和 GitHub Release 按阶段需要另行决定，合入代码不自动代表已经部署。

## 7. 数据与仓库管理

- 源码、非敏感配置模板、少量可合法共享样例和说明进入仓库。
- 密码、令牌、SSH私钥、真实 .env 不入库；大数据集、权重、用户影像、运行数据库与产物单独存储。
- 模型和数据记录来源、版本、许可及必要校验值；不把临时 GPU 磁盘当唯一长期存储。
- 仓库默认私有。改公开、转移、删除、增加管理员、对外发布数据或代码前双方明确确认；不得共享个人账号或认证秘密。
- GitHub 权限与项目分工不同：共同开发不表示共同拥有个人账号仓库。具体邀请和管理员方案见配套指南。
- 本文约定工程协作，不代替知识产权、署名或收益分配协议；相关事项另行确认。

## 8. 约定变更与确认

管理规则通过 PR 修改，写明原因及影响，由双方确认后生效。紧急修复可先处理并立即记录，再补审阅。B 方加入后，应在确认 Issue 或 PR 中明确回复已阅读并接受，或提出修改；仓库创建不代表 B 方已同意。
