## 契约偏差（实现中已兼容，需 B 方确认）

1. `DetectResponse.frame` 的 schema 要求 `index/time_ms/width/height`，`DETECT_API.md` 示例只写前两个。
   后端按 schema 输出四个字段（多给不少给）。
2. 检测页 `detections[]` 用 `label/score`，主应用结果用 `class_name/confidence`；两套并存，由接口层转换。
3. `DetectionResult.image` 在前端 schema 里指向业务 `Image`（含 `file_url/preview_url`），
   而算法输出是 `file_name/sha256/width/height/mode`；后端返回两者的并集。

## 2026-11-04 优化轮（同日第二提交）

在同一天对后端做了一轮总优化，重点是三处缺陷 + 两处并发/IO 优化。命令与前文相同。

### 修复

| 问题 | 现象 | 处理 |
|---|---|---|
| 改几何不改状态 | 拖框后 `review_state` 仍是 `pending`，版本摘要 `changed` 恒为 0 | 只传 `polygon` 时服务端自动置 `modified`；单测 `test_task_lifecycle_end_to_end` 断言 |
| 分片无累计上限 | 客户端不声明 `size` 即可无限刷盘 | 单分片 ≤ `SHIP_CHUNK_SIZE`、累计 ≤ `SHIP_MAX_UPLOAD_BYTES`，超出 422/413；单测 `test_chunk_larger_than_chunk_size_rejected` |
| 过期上传/旧结果不回收 | `var/` 只增不减 | 新增 `maintenance.purge_expired_uploads / prune_result_files / purge_temp_files`，启动执行；单测 `test_maintenance_*` |

### 性能与并发（实测）

| 项 | 优化前 | 优化后 | 测量方式 |
|---|---|---|---|
| `/vision/detect` 请求处理（1.1 MB JPEG） | 写盘 + 重读 + 解码 + SHA256：**23.9 ms** | 内存解码：**10.7 ms** | 同机 5 次取中位，独立脚本（仅这部分开销） |
| 整套 `/vision/detect` 端到端（GPU，1600px，模型已加载） | — | **80 / 83 ms**（冷启 285 ms） | 真实 HTTP 3 次 |
| tiled 的源文件哈希 | 每次调用算 **2 次**全量 SHA-256 | 未变化时 **1 次**（stat 快检） | `test_unchanged_input_hashes_only_once` |
| 大图任务 vs 即时检测 | 同一把锁，任务期间 `/vision/*` 全排队 | 锁下沉到单片，片间让出 | 代码路径 + 18 项算法测试无回归 |
| 预览重复拉取 | 每次全量传输 | `ETag` + `If-None-Match` → **304**（实测） | 实机 HTTP：`etag "33ab4f…-6906-…"`，二次请求 304 |

## 2026-11-04 AI 候选轮（同日第三提交）

### 做了什么

| 项 | 内容 |
|---|---|
| 合并重复实现 | `vision.py::_roi_candidates` 与 `api.py::_candidate_polygon` 各写了一遍"ROI 裁剪 → 模型 → 轮廓兜底"，合并为 `backend/ai_assist.py`，两个入口只做坐标换算与落库 |
| 新增精修模式 | `mode: "refine"` + `existing_polygon`：围绕已有框外扩 25% 取候选，并约束"中心偏移 ≤ 30% 边长、尺寸 0.4–2.5 倍"，防止精修跳到隔壁船 |
| 合理性过滤 | 面积占 ROI 2%–80%、长宽比 1.2–15、最小面积 40px²；不满足直接丢弃（不只是排序） |
| 埋点 | `ai.propose / ai.accept / ai.reject` 写入 `events`，带 `mode/source/quality`，用于后续算采纳率与平均修正次数 |
| 返回值 | 候选新增 `source`（`detect` / `contour`），`confidence` 恒为 `null` |

### 修掉的 bug

长宽比在 `_sane` 与 `create_candidate` 里都写成 `max(sides[0], sides[2]) / min(sides[0], sides[2])`——
`sides[0]` 与 `sides[2]` 是**同一组对边**，比值恒等于 1，导致所有候选被 `ASPECT >= 1.2` 过滤掉，
表现为"AI 候选永远返回 NO_CANDIDATE"。改为对四条边取 `max/min`。

### 测试结果

```text
python -m unittest tests.test_ai_assist -v      →  8 项通过（脚本化检测器，不依赖权重）
python -m unittest discover -s tests            →  51 项通过
                                                   18 算法 + 25 后端 + 8 ai_assist
```

新增的 8 项覆盖：refine 保留近邻候选、refine 拒绝隔壁船、框选补框、面积/长宽比过滤、
模型无命中时走轮廓兜底、非法提示与过小选区报错、契约形状（4 点、quality∈[0,1]）。

### 仍未做

- 没有语义分割模型（SAM2 等），候选质量受对比度限制；`reason` 已如实标注来源。
- 无真实用户采用数据，采纳率/修正次数还没有样本（埋点已就位）。
- 检测页（`/vision/segment`）的候选仍只在前端内存，不落库。

## 2026-11-04 瓦片 / 规划器轮（同日第四提交）

### 交付

| 项 | 内容 |
|---|---|
| 瓦片（显示） | `GET /images/{id}/tile-manifest` 层级清单；`GET /tiles/{id}/{z}/{x}/{y}` 按需生成 JPEG 并缓存，带 ETag/304，越界 404，跨项目 403 |
| 切片预演 | `POST /images/{id}/tile-plan`：复用 `algorithm.plan_tiles`，返回真实网格、覆盖范围与重叠率，**不跑模型** |
| VLM 规划器 | `backend/ai_planner.py`：OpenAI 兼容接口，只回答"这块区域有没有船"；默认 `SHIP_VLM_PROVIDER=none`，失败/超时/解析失败一律返回"没意见"并降级到原几何通道 |
| 接线 | `ai_assist.propose(..., gate=...)`：判定为"无"直接短路返回空 → 端点给出 `422 NO_CANDIDATE` 并附带模型理由 |

GET  /tiles/{id}/0/0/0

GET  /tiles/{id}/0/99/0

瓦片用例：层级计算、按需生成与命中缓存、越界报错、ETag 稳定、切片预演与 `plan_tiles` 一致；

### 明确的边界

- **瓦片只做后端**：浏览器贴块（视口取块、切层、预取、占位）仍需前端实现，约 100–150 行；
  后端单方面做完，界面不会自动出现大图浏览。
- **VLM 未接真实模型**：代码路径与降级已就绪，`SHIP_VLM_PROVIDER=openai` + 本地 Qwen2.5-VL
  或兼容端点即可启用；本轮只用桩验证行为，效果未评估。
- **SAM2 未接**：`ai_assist` 的几何通道仍是"ROI 检测 + 轮廓兜底"，规划器只是加了一道语义门。
